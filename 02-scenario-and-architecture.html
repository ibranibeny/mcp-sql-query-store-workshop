Scenario and two-tier architecture¶

Instruction: 25 minutes · Workshop elapsed: 75 minutes

Adventure Works has a month-end sales procedure whose wide, late, repeated processing can consume a large share of an isolated query-workspace pool. The team needs a contract-equivalent candidate and evidence that survives skeptical review.

Two-VM trust boundary¶

flowchart LR
  U["Facilitator workstation"] -->|"TCP 3389, source IPv4 /32"| P["Admin public IP"]
  P --> AN["Admin NSG + ASG"] --> A["Windows 11 Enterprise admin VM"]
  A -->|"Private DNS + validated TLS, TCP 1433"| SN["SQL NSG + ASG"] --> S["SQL Server 2022 Enterprise VM<br/>10.20.2.10, no public IP"]
  A --> NAT["NAT Gateway"] --> I["Outbound package and source endpoints"]
  S --> NAT

The VNet is 10.20.0.0/16; admin and SQL subnets are 10.20.1.0/24 and 10.20.2.0/24. The SQL VM has no public IP. The admin VM is the only public ingress point, restricted to TCP 3389 from one facilitator IPv4 /32. The SQL NSG permits private TCP 1433 and private RDP only from the admin ASG, then denies other VNet-initiated SQL-tier traffic. No UDP 1434 rule exists. Both subnets disable default outbound access and use NAT Gateway for outbound-only connectivity. DOC-VERIFIED See default outbound access, NAT Gateway design, and application security groups.

Verification exercise¶

After deployment, inspect the plan-card and boundary-readback output. Record pass/fail for: admin NIC has one public IP; SQL NIC has none; public RDP source ends /32; no public 1433/1434 allow exists; SQL private IP is 10.20.2.10; both subnets reference NAT; private DNS resolves sql01.mcpworkshop.internal; and remote SQL reports encrypted transport. If any check fails, do not run the workload.
